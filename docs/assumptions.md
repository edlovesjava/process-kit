# Assumptions the process makes

Every assumption the kit's process rests on, with whether an adopting project may change it
(**tailorable**: change it in `process.toml`, `WORKFLOW.md` or the agent files, with a
decision row) or must keep it (**fixed**: the kit's checks, agents and skills assume it,
and changing it means forking the kit rather than tailoring it). The reason is the
reason, not a justification; if it stops holding, the assumption should change.

| # | Assumption | Tailorable? | Reason |
| --- | --- | --- | --- |
| A1 | **One human approver decides every question, every ADR acceptance and every merge.** Agents propose and implement; they never close a question, accept an ADR, merge or drop an item. | fixed | The whole routing table is built on "down the table as it gets better specified, up the table as a question". Two approvers would need a conflict rule the kit does not have. The approver's name is tailorable (`project.approver`). |
| A2 | **Repository Markdown is the source of truth for tracking.** GitHub issues, project boards and chat are mirrors at best. | fixed | Every agent sees the state on clone, offline, with history; the validator can only check what is in the repository. Issue mirroring is tailorable (`issues.mirror`), its direction is not. |
| A3 | **An ADR beats the spec.** When an accepted ADR and the spec or design document disagree, the ADR wins and the other document gets a pointer. | fixed | A spec that is silently out of date is worse than one with a pointer; the ADR carries the reasoning and the date. Which document is "the spec" is the project's. |
| A4 | **One backlog item per PR, one implementer per item, an item is the unit of review.** | fixed | Acceptance criteria are checked per PR; the reviewer, the journal and `merge-sync` all key on the item id. Item size is tailorable by how the planner writes them. |
| A5 | **Architecture and process review at every milestone boundary gate the next milestone.** The next milestone's first code item waits on the blocking findings of both. | tailorable (cadence) | Reviewing the whole, not the diff, is where the source project found its design errors before they were cast into immutable data. The cadence (every milestone, every other, by calendar) is a decision row and a `WORKFLOW.md` edit; skipping reviews entirely removes two roles and is a fork. |
| A6 | **Agents propose and never decide.** Every proposal (option, recommendation, draft) is written where the approver can read and act on it. | fixed | See A1. It is also why each agent's definition ends with "do not edit" lists. |
| A7 | **A cloud session pushes its branch before anything else.** | fixed (for cloud) | A branch with no commits is not on origin, so the session cannot be teleported or opened in a terminal. It costs one command and a missed push cost the source project a session. Irrelevant for purely local work. |
| A8 | **Builds are warning-clean and CI is never changed to make it pass; the code is fixed.** | fixed | The agents are told this verbatim. A project with a different tolerance edits its own build, not the rule. |
| A9 | **Small, focused commits; do not touch unrelated files.** | fixed | Reviews read diffs against one item's acceptance criteria; an unrelated change has no criteria to be checked against. |
| A10 | **Every interface a component emits (event, message, API, CLI command, file format) is documented before its producer merges.** | tailorable (where) | Consumers, tests and reviews need the contract before the code. The kit does not say where the catalogue lives; the project names the file in `CLAUDE.md`. |
| A11 | **Roles run on fixed models and tool allowlists.** Research on the lead model, planning, project and program management, review and architecture on Opus, implementation on Sonnet, operations on Haiku. | tailorable | Each role runs on the cheapest model that does it well; that judgement moves with the models. Change `process.toml` `[roles]` and the agent file's `model` together, with a decision row. |
| A12 | **Milestones are the unit of planning and review.** Each has a one-line acceptance test; items carry a milestone; the milestone list is finite and in `process.toml`. | tailorable (names and count) | Reviews need a boundary; stale checks need a horizon. Names are the project's. |
| A13 | **Statuses are `idea`, `blocked`, `ready`, `in-progress`, `review`, `done`, `dropped`, and `ready` has a precise meaning:** every dependency `done`, every linked question `answered`. | partly fixed | The validator reasons about `ready`, `blocked`, `in-progress`, `review`, `done` and `dropped`; those stay. Extra statuses may be added. |
| A14 | **Questions are closed only by the approver or by an accepted ADR, and are append-only in spirit:** progress is dated lines, never a rewritten entry. | fixed | A question that an agent closes is a decision an agent made (A6). |
| A15 | **Decisions are append-only; a changed mind supersedes, never edits.** Same for ADRs, with the one amendment exception while no code depends on the record. | fixed | The log is how a later session learns why; an edited row loses the why. |
| A16 | **Every agent dispatch and every human decision is one journal row, written the same day.** | tailorable (on/off) | The process review is counted from the journal; without rows it is opinion. `journal.enabled = false` turns the checks off for a project that will not review its process. |
| A17 | **SITREP entries are dated handoffs, newest first, corrected by dated notes rather than silent edits.** | fixed | A wrong root cause stood unmarked in the source project for a session; the dated correction is the fix. |
| A18 | **The validator is a copy the project owns, run with `python3 -I`, standard library only, Python 3.11 or newer.** | fixed | CI and cloud sessions run it with nothing installed. A project may extend its copy; the kit's updates are then merged by hand. |
| A19 | **The agents are copied into `.claude/agents/` as well as shipped in the plugin.** | tailorable | Cloud sessions do not load project-scope plugins, and the source project runs in cloud sessions. A purely local team may rely on the plugin alone (`--no-agents`). |
| A20 | **Only the plugin's skills and agents are needed; no MCP server, no network.** | fixed | The process is files and conventions. Anything needing a service is the project's. |
| A21 | **The approver's time is the scarce resource.** Agents batch what they need decided, give a recommendation with every question, and never ask what the record already answers. | fixed | It is why the researcher recommends, the PM summarises in 30 lines and the journal counts human turns. |
