# Prior art and comparison: where process-kit sits, 2026-10-31

Asked by Ed (B-023): how does the kit compare with Linear, ClickUp Brain, Jira AI and the
rest? Three researchers ran in parallel on three clusters: AI and agent features in issue
trackers; spec-driven and role-based frameworks for AI coding agents; and decision-record,
governance and process-measurement tooling. Primary sources were read where reachable.
Many vendor hosts were not reachable from the cloud sandbox (list at the end), so facts
from them come from search-engine extracts of the primary page or from secondary coverage
and are marked **(extract)**; anything from memory is marked **(recall, verify)**. GitHub
star counts and last-commit dates are as of 2026-10-30 or 31.

The kit's features the comparison is made on:

| # | Feature |
| --- | --- |
| F1 | One human approver gates every merge, ADR acceptance and closed question; agents propose |
| F2 | Repository Markdown is the source of truth; a validator refuses `ready` while a dependency or question is open |
| F3 | Role agents pinned to a model tier and a tool allowlist |
| F4 | ADRs beat the spec when they disagree |
| F5 | Questions register only the human closes; append-only decision log |
| F6 | Activity journal (dispatches, reruns, human turns) reviewed by a program manager; architecture and process reviews gate the next milestone |
| F7 | Plugin for behaviour, scaffold copies owned files; offline, standard library only |

## Summary

1. **Issue trackers are complements, not competitors.** In 2026 Linear, Jira, ClickUp,
   Asana, monday, Notion, GitHub and GitLab all shipped "give an issue to an agent, a human
   reviews the result". None keeps tracking in the repository, none fixes roles or models,
   none has decision records, a questions register or process metrics. The kit's
   `issues.mirror` switch is the touchpoint, and the trackers' delegation models (Linear's
   delegate-not-assignee, Jira's private-then-publish output) are worth copying as
   conventions.
2. **Spec-driven frameworks are the real prior art, and they are big.** Spec Kit (144k
   stars), OpenSpec (73k), superpowers (310k), BMAD (55k), Task Master (28k), compound
   engineering (26k). They cover repository Markdown as the source of truth with a human
   approval before implementation (F2 in part), two of them validate with a script
   (OpenSpec `validate --strict`, Task Master dependency-aware `next`), and two pin roles to
   models and tools (BMAD personas, Anthropic's `feature-dev` agents). Their vocabulary
   (constitution, spec, plan, tasks, change) is what adopters will already speak.
3. **Not found anywhere else, on this evidence:** a journal that counts dispatches, reruns
   and human turns and is reviewed by a program-manager agent at a milestone boundary (F6);
   one named approver gating merges, ADR acceptance and question closure together (F1 and
   F5); the rule that an accepted ADR outranks the spec, stated as a rule (F4); and an
   offline, standard-library validator that hard-refuses `ready` on an open dependency or
   question (F2). The closest relatives are Spec Kit's constitution-over-plan gates (checked
   by the LLM, not a script), Task Master's dependency gating (JSON, needs API keys) and
   BMAD's agent-run retrospective (per story group, no counts).
4. **Reinvented, and should be replaced with the standard:** the ADR format (MADR 4.0
   already has `decision-makers`, `consulted`, `informed` and `superseded by`), the
   Markdown backlog format (Backlog.md has files, front matter, dependencies, acceptance
   criteria, a `doctor` command and an MCP server), and dispatch counting (Claude Code's
   OpenTelemetry events already emit agent name, retry attempt and user-turn source).
5. **The kit's position, in one sentence:** the frameworks tell an agent how to build one
   feature well; the trackers tell a human what an agent did; the kit is the only one of the
   set that runs a whole project's governance (who decides, what is recorded where, how the
   process itself is measured and reviewed) from the repository. That is the pitch, and it
   is also the gap the others could close in a release.

## Cluster A: issue trackers

**Linear.** Linear Agent (public beta 2026-03-24, all plans) is a workspace member you
assign, mention or add to projects; it triages, drafts updates and since 2026-06-11 runs
cloud coding sessions through Claude Code or Codex that return a PR reviewed in-app with
Linear Diffs (2026-05-27). Third-party agents (Cursor, Devin, Codex, Codegen, Cyrus for
Claude Code) use the Agents API: an issue is *delegated*, the human stays assignee;
sessions move pending, active, awaitingInput, error, complete; a stop signal must be
honoured; the Agent Interaction Guidelines say final responsibility stays with a human.
Triage Intelligence suggests team, assignee, labels and duplicates. The MCP server exposes
CRUD. Sources (extract): linear.app/changelog 2026-03-24, 2026-06-11, 2026-05-27,
2026-04-23; linear.app/developers/agents, /aig, /agent-best-practices;
changelog 2025-08-14 (Product Intelligence).

**ClickUp.** Brain is the AI layer, Brain MAX the desktop app, Super Agents (formerly
Custom Agents) are workspace agents with instructions, triggers, skills, knowledge and
memory, with a catalogue and a certification programme; Autopilot Agents live in one
List, Folder or Space. Help docs say agents "seek human approval for critical decisions"
and a Super Agents Audit Log records actions; a named "Approval Mode" appears only in
marketing (recall, verify). Sources (extract): help.clickup.com articles 31010910371991,
37092796379927, 36455020912919, 31012020810775; clickup.com/brain/agents.

**Jira and Atlassian Rovo.** Agents in Jira (2026-02-25) put Rovo agents, space-built
agents and third-party agents (Copilot coding agent, public preview 2026-03-05) in the
assignee field or on a board column; their output lands in a private Agents section until
the assigner publishes it. Rovo Dev opens a linked draft PR from a work item and a Code
Reviewer checks PRs against acceptance criteria. AI Work Breakdown proposes child items
to accept, edit or decline. Team '26 (May 2026) opened the Teamwork Graph through CLI and
MCP and shipped Rovo Studio and org-wide agent inventories. Confluence's Decisions
blueprint builds a decision index with a status macro; DACI exists; a third-party app adds
ADR statuses. Sources (extract): support.atlassian.com "Collaborate on work items with AI
agents"; atlassian.com blog posts Feb, May and Aug 2026; github.blog changelog 2026-03-05.

**Briefly.** Asana AI Teammates (Spring 2026) are assignable with scope and checkpoints.
monday.com agents (launched May 2026) are full users under the permission model with
per-action approval. Notion Custom Agents (2026-02-24) are triggered by database changes
or schedules, zero access by default, every run logged with trigger, action and reason,
the nearest thing to a per-run journal in this cluster. GitHub Copilot coding agent opens
a draft PR from an assigned issue; the assigner's approval does not count toward required
approvals and Actions wait for a human click, the hardest gate found; AGENTS.md is read
since 2026-06-23; sessions show on Projects boards. GitLab Duo Agent Platform (GA
2026-01-15) runs Planner, Security and Data Analyst agents and issue-to-MR flows with
checkpoints; an Impact dashboard counts adoption and credits. Sources (extract):
asana.com spring-release-2026; ir.monday.com 2026; notion.com/product/agents;
docs.github.com review-copilot-prs and github.blog changelogs 2026-03-13, 2026-03-26,
2026-06-23; about.gitlab.com 2026-01-15 and docs.gitlab.com custom flows.

## Cluster B: spec-driven and role-based frameworks

**GitHub Spec Kit** (github.com/github/spec-kit, 144k stars, last commit 2026-10-30,
release 1.2.5, MIT). The `specify` CLI installs slash commands and templates. A
constitution in `.specify/memory/constitution.md` holds "immutable principles that govern
how specifications become code"; each feature gets a branch and `specs/NNN/` with spec,
plan, research, data model, contracts and tasks. The plan template has pre-implementation
gates checked against constitution articles; a failed gate needs a justification in a
Complexity Tracking table. `[NEEDS CLARIFICATION]` markers must be cleared before tasks.
Gates are LLM self-checks, not a script; shell scripts only check that files exist.

**AWS Kiro** (kiro.dev, extract; github.com/kirodotdev/Kiro issue tracker). Specs are
`requirements.md` with EARS acceptance criteria, `design.md`, `tasks.md`; steering files;
agent hooks on file events; the Spec agent requires approval between the three phases,
"Quick Spec" skips them. Closed-source IDE and CLI.

**OpenSpec** (github.com/Fission-AI/OpenSpec, 73.5k, v1.16.0 2026-10-30, MIT). Living
specs plus per-change proposal, delta specs (ADDED, MODIFIED, REMOVED with WHEN/THEN
scenarios), design and tasks; propose, apply, verify, archive. `openspec validate
--strict` checks requirement and scenario shape, duplicates and untracked tasks; archive
refuses malformed deltas. The strongest validator in the cluster.

**BMAD Method** (github.com/bmad-code-org/BMAD-METHOD, 54.8k, last commit 2026-10-18,
MIT). Named persona agents (Analyst, PM, PO, Architect, Developer, UX, Technical Writer;
earlier SM, test architect). Stories flow backlog, drafted, ready-for-dev, in-progress,
review, done in story files plus `sprint-status.yaml`, which issues show drifting. The
human approves PRD and architecture and moves stories to ready-for-dev; `bmad-retrospective`
reviews a completed story group against evidence. No model pinning found.

**claude-task-master** (github.com/eyaltoledano/claude-task-master, 28.3k, last commit
2026-04-23, MIT plus Commons Clause). PRD to `tasks.json` with dependencies, statuses and
subtasks; `next` returns only tasks whose dependencies are done; `validate-dependencies`;
`--ready` filter added 2026; MCP server with 36 tools; needs API keys. Model roles are
main, research and fallback, not task roles.

**CCPM** (github.com/automazeio/ccpm, 8.4k, last commit 2026-10-19, MIT). PRDs to epics to
task files synced to GitHub issues, parallel agents in worktrees. Bash status scripts, no
schema validation. **Agent OS v3** (github.com/buildermethods/agent-os, 5.6k, 2026-10-07,
MIT) refocused on standards injection; planning files but no validation. **Conductor**
(github.com/gemini-cli-extensions/conductor, 3.8k, 2026-09-01, Apache-2.0): product,
tech stack, workflow and tracks files, per-track spec and plan, `conductor-review` and a
`conductor-revert` keyed to plan tasks. **compound-engineering** (github.com/EveryInc/
compound-engineering-plugin, 25.8k, 2026-10-31, MIT): brainstorm, plan, work, simplify,
review, compound; `/lfg` loop opens PRs and "does not merge unless granted permission";
`ce-compound` writes learnings to `docs/solutions/`. **superpowers** (github.com/obra/
superpowers, 310k, v7.0.1 2026-10-21, MIT): brainstorming, plans, subagent-driven
development with a fresh implementer and reviewer per task, merge or PR chosen at the end.
**Anthropic claude-plugins-official `feature-dev`** (45.6k, 2026-10-30, Apache-2.0):
seven phases, `code-architect` pins `model: sonnet` with a tool allowlist, writes no
tracking. **Lineage:** MetaGPT's SOP roles (PM, Architect, Project Manager, Engineer) and
ChatDev's role chat chain, both without a human gate.

## Cluster C: decision records, repository trackers, governance, measurement, cadence

**ADR tooling.** Nygard's 2011 post (via arc42 FAQ; cognitect.com unreachable) sets the
five sections and the status-only-mutation rule. MADR 4.0.0 (github.com/adr/madr,
2024-09-17) adds front matter `status` ("proposed | rejected | accepted | deprecated |
superseded by ADR-0123"), `date`, `decision-makers`, `consulted`, `informed` and an
optional Confirmation section on how compliance is checked; markdownlint only.
adr-tools (npryce) rewrites the superseded record's status mechanically and looks
unmaintained. log4brains states "an ADR is immutable, only its status can change" and
infers dates from git. Backstage's ADR plugin indexes and displays, never validates.
2026 pieces on ADRs for agents (Mneme HQ, Jul 2026; AsDecided, Aug 2026, extract) argue
for stable ids, explicit status and scope, and precedence semantics between conflicting
ADRs. **The rule "an accepted ADR beats the spec" was not found anywhere**; one source
argues the opposite (spec governs, ADR records rationale). Spec Kit's constitution is the
nearest formal precedence.

**Repository-as-tracker tools.** Backlog.md (github.com/MrLesk/Backlog.md): Markdown
tasks with front matter, `--dep`, acceptance criteria and definition-of-done checklists,
`backlog doctor`, MCP server; its agent guidelines say to confirm dependencies before
starting, but the CLI does not refuse a status change. git-bug stores issues as git
objects, offline, with bridges; no workflow validation. Taskwarrior and Obsidian Tasks
have dependencies as query state. No linter that validates front-matter status against
dependency state was found; the kit's `ready` rule appears novel in this set.

**Human-in-the-loop governance.** Claude Code permission modes and hooks
(code.claude.com/docs) are the baseline: `PreToolUse` deny, `PermissionRequest`,
`SubagentStart`/`SubagentStop`, `TaskCreated`/`TaskCompleted`; tool allowlists are native,
one-approver gating is not. AGENTS.md (github.com/agentsmd/agents.md) is a README for
agents with no schema. Google ADK tool confirmation (ADK 1.14+) and LangGraph `interrupt()`
(extract) give per-action approval. Thoughtworks Radar vol. 34 (Apr 2026, extract):
"putting coding agents on a leash", feedforward against feedback controls; spec-driven
development and Spec Kit at Assess; coding-agent swarms at Caution. Dhanorkar, Passi and
Vorvoreanu (arXiv 2606.05391, Jun 2026, extract) name four oversight forms: a priori
control, co-planning, real-time monitoring, post hoc review; developers "opt for efficient,
not perfect, oversight". RACI-for-agents pieces share one rule: a single accountable human
per autonomous action.

**Measuring agent work.** Claude Code OpenTelemetry (code.claude.com/docs/en/
monitoring-usage): `token.usage` and `cost.usage` carry `query_source` (main, subagent,
auxiliary) and `agent.name`; `active_time.total` has type user or cli; events
`user_prompt`, `tool_decision` (source config, hook, user), `api_error.attempt` for
retries, `prompt.id` to rebuild a turn. Dispatches, human turns and reruns are all
derivable; nothing ties them to a review cadence. Copilot metrics API and Cursor
analytics measure acceptance, not process. DORA 2025 "State of AI-assisted Software
Development": AI amplifies; throughput up, stability down; the seven-capability AI model
(clear stance, healthy data, AI-accessible internal data, strong version control, small
batches, user focus, quality platforms); no cadence. "Beyond Code Generation" (arXiv
2609.04681, 2026, extract) proposes human escalation rate, first-pass qualification,
qualified output per reviewer-hour, escaped-failure rate and cost variance: the closest
published analogue to the journal's counts. MSR 2026 "Behind Agentic Pull Requests"
(extract): interventions on agent PRs are about 58% guidance, 21% decision, 17% direct
code change.

**Milestone-boundary reviews, the lineage.** RUP gates each phase at a major milestone
and the Lifecycle Architecture review asks whether the architecture is stable. Shape Up
holds a betting table in a cool-down after each cycle, and unfinished work trips a circuit
breaker and is re-pitched. SAFe Inspect and Adapt pairs measurement with a retrospective
before the next increment. The Team Software Process makes a data-driven postmortem a
phase of every cycle, fed by time and defect logs. The kit's paired architect and
program-manager reviews are RUP's architecture gate plus TSP's measured postmortem, on
Shape Up's cadence; the journal is the TSP data log.

## What the kit has that was not found elsewhere

- F6 in full: a dispatch, rerun and human-turn journal reviewed by a program-manager
  agent at a milestone boundary, gating the next milestone. Closest: BMAD's per-story-group
  retrospective (no counts), Notion's per-run log (no review), Claude Code telemetry (no
  review).
- F1 with F5: one named approver for merges, ADR acceptance and question closure
  together, with a questions register agents cannot close. Closest: Copilot's non-counting
  approval (merges only), Spec Kit's clarification markers (no owner).
- F4 as a stated rule. Closest: Spec Kit's constitution-over-plan gate.
- F2's hard gate in an offline, standard-library validator the project owns. Closest:
  Task Master (JSON, API keys), OpenSpec (Node 22, shape checks, no readiness gate),
  Backlog.md (advisory).

## Where the kit reinvents something that exists

- ADR format: MADR 4.0 has the front matter and the supersession status string already.
- Markdown backlog: Backlog.md has the file format, dependencies, acceptance criteria and
  an MCP server; the kit's additions are the hard gate and human-only closure.
- Dispatch counting: Claude Code telemetry already emits it; the hand-kept journal is
  defensible under invariant 3 (offline, no service) but should say so.
- Tool allowlists and permission gating: native to Claude Code; the kit adds the per-role
  pinning only.
- Repository Markdown with a human approval before implementation: Kiro, Spec Kit,
  OpenSpec, Conductor, superpowers and CCPM all do it. The kit cannot claim this alone.
