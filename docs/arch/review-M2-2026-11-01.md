## 4. Findings, ranked

### Blocking (decide before the next milestone's first code item)

**B1. Scaffolded copies carry no provenance, and the documented update path does not exist.** *verified.*
- **Where:** `tools/scaffold.py:52-60` (`place`), `:91-97`; ADR-0001 Consequences; `docs/tailoring.md:99-102`; `docs/assumptions.md` A18; D-013; B-018.
- **What:** The scaffold writes the validator, agents, templates and workflow with no record of the kit version or content it wrote. ADR-0001 says updates arrive by "`scaffold --force` on chosen paths", but the scaffold has no path filter: `--force --dry-run` would rewrite all 27 files, including the project's `activity.md`, `decisions.md`, `questions.md` and B-001.
- **Why:** D-013 requires the kit to update and tune copies after the first scaffold. M3 (B-014, B-015) creates the first two adopters. Without a base recorded at scaffold time, B-018 can only do a two-way diff, so it cannot tell "the project changed this" from "the kit changed this", and those two adoptions would need re-baselining by hand. The one documented update command destroys tracking data.
- **Proposal:** Before B-014 starts: (a) the scaffold writes `project/process-kit.lock` (TOML, read only by the scaffold and the future update skill) with the kit `version` from `plugin.json`, the git commit if available, and a sha256 per copied path; (b) add `--only PATH` (repeatable) so `--force` can target chosen paths, and refuse `--force` without `--only` once a lock file exists; (c) A18 and `docs/tailoring.md` say so. Tests: `test_scaffold_writes_lock_with_hashes`, `test_force_only_limits_paths`. B-018 then depends on this item and reads the lock as its merge base. Record the design in ADR-0002 (section 6).
- **Cost:** S.

**B2. ADR-0001 is still Proposed while code and four decisions rest on it, and D-013 has changed it.** *verified.*
- **Where:** `docs/adr/0001-plugin-for-behaviour-scaffold-for-files.md` (Status: Proposed); D-005, D-006, D-013, D-015; B-013 (`ready`, role human).
- **What:** The whole M0 to M2 structure implements Option C, but the ADR is unratified. D-013 turns its "updates reach adopting projects by hand" consequence into a requirement, and D-015 adds the kit's own `.claude/agents/`, neither of which the ADR text reflects.
- **Why:** Invariant 2: ADR acceptance is Ed's. M3 puts this structure into two more repositories; a rejection or a material change after that rewrites both adoptions. `docs/adr/README.md` stops amendments once code depends on an ADR, and code already depends on this one; the record should be settled now rather than later by supersession.
- **Proposal:** Ed takes B-013 before M3. Recommendation: accept ADR-0001 with its Consequences updated (while it is still Proposed) to cite D-013 and D-015, and point to ADR-0002 for the update mechanism (B1).
- **Cost:** XS (Ed), plus XS for the edit.

### Should fix before the next milestone

**S1. The hook has no test and takes the project root from the payload cwd.** *verified.*
- **Where:** `scripts/check_hook.py:26-35`; `hooks/hooks.json` matcher `Write|Edit`; N-007.
- **What:** With `cwd` set to `<root>/docs` and the edited file under `<root>/project/backlog/`, the hook exits 0 without validating. An edit made after the session `cd`s into a subdirectory is never checked. Tools other than Write and Edit that change files (MultiEdit, NotebookEdit, if the running CLI offers them) are not matched (*inferred*).
- **Why:** G3, and B-015's acceptance needs "the hook reported at least one error". A silent skip will look like a clean edit.
- **Proposal:** Find the root by walking up from the edited file's parents to the first directory holding `project/process.toml`, and ignore cwd. Add `tools/tests/test_hook.py`, which runs the script as a subprocess with the payloads used here: clean edit, broken item (exit 2), relative path, edit outside `project/`, subdirectory cwd (exit 2 after the fix), missing `file_path`, non-JSON, empty stdin, `tool_input: null`, a list payload, a repository without `process.toml`. Widen the matcher after checking the current tool names. N-007 moves to `met`.
- **Cost:** S.

**S2. B-020 (`--strict` in CI) cannot pass while the kit is both plugin and project.** *verified.*
- **Where:** `CLAUDE.md` at the plugin root; B-020; N-005.
- **What:** `claude plugin validate . --strict` exits 1 on "CLAUDE.md at the plugin root is not loaded as project context". The file is the kit's own project instructions, so the warning is permanent.
- **Why:** If B-020 is built as written, it is either red on main or someone weakens the check, which the Conventions forbid.
- **Proposal:** Amend B-020 (question in section 6): run `claude plugin validate . --json` and fail on any error, or on any warning except the one known `CLAUDE.md` warning, matched by its message. Do not restructure the repository (moving the plugin to `plugin/` breaks `${CLAUDE_PLUGIN_ROOT}/tools` and every path in the docs). Confirm the CLI validates without authentication on a CI runner; that was not tested here because this session's auth state is unknown (*inferred*).
- **Cost:** S.

**S3. A project cannot add a check without forking its validator.** *inferred.*
- **Where:** `tools/check.py:375-402` (`run`); `docs/tailoring.md:97-102` ("Extend it"); B-014 ("its validator is replaced by the kit's copy").
- **What:** The only way to extend checks is to edit `project/tools/check.py`, which turns the copy into a fork that B-018 can no longer update cleanly.
- **Why:** G2 and D-013. The source project will very likely have a check the kit lacks, so B-014 forks the copy on its first day.
- **Proposal:** `run()` loads `project/tools/check_local.py` if it exists (`importlib.util.spec_from_file_location`, stdlib, works under `-I`) and calls `check(root, cfg, result)`. The scaffold never writes it. `docs/tailoring.md` says to extend there. Test with one local check that adds an error. Ask Q-007 first.
- **Cost:** S.

**S4. Invariant 5: five validator rules are not stated in the template they check, and one rule differs from its prose.** *verified.*
- **Where:** `templates/project/backlog/README.md` Rules; `templates/project/activity.md`; `tools/check.py:272-275, 296-301, 286-291, 303, 323-325`.
- **What:** The backlog README does not state that the id must match the file name and be unique, that `depends_on` and `questions` must name things that exist, that `updated` must be `YYYY-MM-DD`, or that stale items are warned. `activity.md` does not say that Runs and Human turns must be whole numbers or that a row needs nine cells. The README says `ready` needs every question `answered`, but `check.py:303` blocks only on `open`, so a `superseded` question passes.
- **Why:** Invariant 5 and G4. A reader following the template by hand would not predict these errors.
- **Proposal:** Add one Rules line each, mirrored in the kit's own `project/backlog/README.md`. Settle `superseded` with Q-009, then make the prose and the code agree.
- **Cost:** XS.

**S5. N-004 has no measure of "every check has a test".** *verified.*
- **Where:** `tools/tests/test_check.py`; the five config messages and the three scaffold CLI paths listed in N-004 above.
- **Proposal:** Add the eight missing tests. Add a meta-test that parses `check.py` with `ast`, collects the literal fragment of every `errors.append`, `warnings.append` and `problems.append` f-string, and fails if a fragment appears in no test. N-004 then becomes `met` on that test.
- **Cost:** S.

**S6. N-001 relies on convention.** *verified.*

- **Proposal:** Add `test_stdlib_only`, which walks `tools/` and `scripts/` with `ast` and asserts that every import is in `sys.stdlib_module_names` or is a sibling module. Run the unit job on a 3.11 and 3.13 matrix, and pin `tracking.yml` to 3.11, the floor the kit promises. N-001 then becomes `met`.

## 5. Looking ahead

**M3 (B-014 source project, B-015 fresh project).** *Helps:* the scaffold is idempotent and never overwrites; the CLAUDE.md merge path exists (`test_existing_claude_md_is_left_alone`); the whole vocabulary is config, so the source project's roles and milestones fit without code; the journal accepts `reconstructed` rows as they are; an existing `.claude/agents/` is skipped, so the source project keeps its tuned agents. *Hurts:* both adoptions happen before provenance exists (B1); the source project's extra checks force a fork (S3); the hook may stay silent in B-015's loop (S1). *Decision points:* B-013 (ADR-0001); the lock format and `--only` (ADR-0002); Q-007 (extension seam); whether B-014 adopts the kit's agents or records its own as tuned copies.

**M4 (B-016 to B-020).** *Helps:* `check.py` is a good oracle for B-017 evals, since every skill's output can be asserted by running it; `load_journal` is one function, so a second row shape (B-016) has one place to go. *Hurts:* every new validator rule (B-016, and B-025 `kind`/`flow`, B-026) has to reach adopters' copies, which makes B1 and B-018 the critical path for everything after M3; B-020 needs S2 decided; `KNOWN_SECTIONS` (`check.py:41`) makes a new config section an error in older copies, so a `flow` key should sit in an existing section or older copies must tolerate unknown keys. *Decision points:* Q-008 (plugin validation in CI); the journal shape after the D-014 comparison.

**Ideas B-024 to B-029.** Optional front-matter keys are already tolerated (`parse_front_matter` keeps any key), which suits `kind`. Branch and commit rules (B-028) need git, but `check.py` is a pure file reader: keep git-aware checks in a separate CI script so the validator stays runnable on a bare checkout (decision point for B-028). Multi-repository (B-029): `check.py` hardwires `<root>/project` and the hook hardwires `<cwd>/project`. With S1's walk-up, a code repository without `project/` is a correct no-op, and a tracking repository works through `--root`. The open choice is the tracking-repository versus primary-repository option, which B-029 already frames.
